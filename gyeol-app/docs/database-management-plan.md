# DBMS 전환 및 운영 계획

작성일: 2026-11-15. 상태: 설계안. DB 구축·데이터 이전·배포는 수행하지 않았다.

진행 업데이트: 로컬 구현·기본 SQLite 이전·백업·검증을 완료했다. 실제 파이 배포와 현장 부하 검사는 SSH 접속 대상 확인 후 진행한다. [구현 및 검증 결과](database-execution-2026-11-15.md), [운영 안내](database-operations.md)를 따른다. 아래 내용은 최초 설계 기준이다.

현재 소스, 로컬 `packages/server/data/gyeol.json`, `deploy/pi` 배포 구성을 기준으로 한다. 배포 서버의 실제 데이터와 부하는 확인하지 않았다. 로컬 조사 시 플레이어 1,008명(사람 8, AI 1,000), 대국 15개, 레이팅 이력 25개이며 이 수치는 운영 이전 시 기대값으로 고정하지 않는다.

## 1. DBMS와 적용 범위

1차 DBMS는 SQLite로 한다. 단일 Raspberry Pi 4B·4GB, 단일 Node 서버라는 현재 배포 형태와 작은 실제 쓰기량에 맞춘 선택이다. AI 프로필 1,000개는 동시 접속자나 동시 쓰기 1,000건을 의미하지 않는다.

SQLite는 DBMS이며 SQL, 인덱스, 외래키, 트랜잭션을 사용한다. 저장 형식이 파일이라는 점과 현재 JSON 전체 덮어쓰기 방식은 구별한다. WAL에서도 쓰기는 한 번에 하나이므로 짧은 트랜잭션으로 운영한다. [SQLite 사용 지침](https://www.sqlite.org/whentouse.html), [WAL 문서](https://www.sqlite.org/wal.html)

| 항목 | 1차 결정 |
|---|---|
| 운영 DB | `/var/lib/gyeol/gyeol.sqlite` |
| 개발 DB | 별도 개발 경로. 운영·이전 검증·테스트 DB를 분리 |
| Node 드라이버 | `better-sqlite3`. 구현 시 지원 Node 및 Linux ARM64 조합을 실제 검증하고 버전 고정 |
| 데이터 접근 | 명시적인 SQL과 prepared statement, SQL 마이그레이션 파일 |
| 서버 구조 | WebSocket 서버 → 비동기 Repository → 전용 DB worker → SQLite |
| 초기 서버 수 | 대국을 처리하는 애플리케이션 프로세스 1개 |
| 서버 관리 범위 | 온라인 계정·토큰·대국·수순·레이팅·전적·이력 |
| 기기 유지 범위 | 설정·AI 로컬 전적·퍼즐 진행·오프라인 기보·분석 캐시 |

DB worker는 동기 SQL과 디스크 동기화가 WebSocket 이벤트 루프를 오래 막는 상황을 피하기 위한 것이다. 규칙 검증과 레이팅 계산에 필요한 순수 모듈을 worker에서도 사용하며 AI 모델 추론은 DB 트랜잭션 밖에서 한다. Repository 경계를 비동기로 만들어 향후 PostgreSQL 구현으로 교체할 여지를 둔다. SQL 방언·잠금·배포는 별도 이전 작업이 필요하며 단순 설정 변경으로 전환되지는 않는다.

## 2. 테이블 설계

ID는 기존 문자열을 그대로 `TEXT`로 보존한다. 시각은 기존 코드와 맞춰 UTC Unix epoch 밀리초 `INTEGER`, Glicko-2 수치는 `REAL`로 저장한다. 화면용 반올림 값은 원본 점수와 분리한다. 테이블에는 가능한 범위에서 `STRICT`, `NOT NULL`, `CHECK`, 외래키를 적용한다.

| 테이블 | 키와 주요 내용 |
|---|---|
| `players` | `id PK`, 이름, `is_bot`, `bot_roster_version`, 생성·최근 접속 시각 |
| `player_tokens` | `id PK`, `player_id FK`, `token_hash UNIQUE`, 생성·마지막 사용·폐기 시각 |
| `player_ratings` | `player_id PK/FK`, `rating`, `rd`, `vol`, `ranked`, `rated`, 승패, `rating_at`, 최고·최저점, `history_complete` |
| `games` | `id PK`, 두 참가자 FK, 코드, 랭크 여부, 시간 모드, 상태, 승자·종료 사유, 시계, 생성·수정·종료 시각, `revision`, `ply_count`, `rating_applied_at` |
| `game_moves` | `(game_id, ply) PK`, 행동 정수, 둔 측, 기록 시각. 패스도 한 행으로 보존 |
| `rating_events` | `id INTEGER PK`, 플레이어 FK, 대국 FK(nullable), 출처, 시각, 변경 전후 점수·RD·변동성, 표시 증감, 점수 제한 사유, 정책 버전 |
| `schema_migrations` | 버전 PK, 파일 체크섬, 적용 시각 |

관계는 `players 1:1 player_ratings`, `players 1:N player_tokens`, `players 1:N rating_events`, `games 1:N game_moves`, `games 1:N rating_events`이다. `games`의 초록·갈색 참가자 각각이 `players`를 참조한다.

추가 설계 규칙:

- 대기방의 빈 자리는 nullable로 허용하되 진행·종료 대국은 양측 참가자가 있어야 한다. 동일인이 양측을 맡을 수 없다.
- `status`, `mode`, `end_reason`, `winner`는 허용값을 제한한다. 종료 상태와 승자·사유·종료 시각의 일관성도 검사한다.
- `ply`는 1부터 연속, 현재 규칙의 `action`은 0~784, 플레이어 색은 1 또는 -1이다. 연속성과 합법 수는 트랜잭션 내부의 규칙 엔진이 검증한다.
- `games.rule_version`, `initial_board_json`, `initial_player`를 명시적으로 보존한다. 초기 배치는 작고 고정된 값이므로 JSON 한 컬럼으로 저장하되 길이·값은 규칙 엔진으로 검증한다.
- 점수 변화·제한 사유는 `games`에도 양측 결과 스냅샷으로 보존한다. `rating_events`는 감사 이력이며 새 대국에서는 같은 트랜잭션에서 함께 기록한다. 과거 스냅샷만 있고 상세 이력이 없는 대국도 표시할 수 있어야 한다.
- `game_moves.recorded_at`, 과거 대국의 정확한 `finished_at` 등 원본에 없는 값은 nullable로 둔다. 종료 시각 대용으로 원본 `updatedAt`을 사용할 경우 `time_source='legacy_updated_at'`로 구분한다. 실제 수별 시각을 만들어내지 않는다.
- `rating_events.source`는 `baseline`, `game`, `legacy`를 구분한다. 대국 이벤트에는 `UNIQUE(game_id, player_id)`를 적용한다. 레거시 이벤트에는 `(player_id, legacy_index)` 고유값을 둔다.
- 레거시 이력은 당시의 정수 점수만 알 수 있다. 변경 전 점수·RD·변동성·대국 연결은 확인 가능한 경우에만 채우며 없으면 NULL이다. 원본 배열 순서도 보존한다.
- AI도 플레이어·레이팅 행을 갖는다. AI 상대 승패와 실제 전적은 기록하되 고정 레이팅은 갱신하지 않는다. 실제 쓰기가 없는 AI의 인증 토큰은 이관하지 않아도 되지만 기본 이전은 호환성을 위해 기존 토큰을 모두 해시로 보존한다.
- 계정·기보는 운영 중 단순 삭제하지 않는다. 탈퇴 처리가 필요해지면 별도 익명화 정책을 설계한다. 외래키 삭제 기본값은 `RESTRICT`로 한다.

## 3. 조회와 인덱스

| 조회 | 인덱스·처리 방식 |
|---|---|
| 기존 토큰 로그인 | `player_tokens(token_hash)` UNIQUE, 폐기 여부 검사 |
| 내 최근 대국 | `games(green_id, updated_at DESC, id DESC)` 및 갈색 대응 인덱스. 양쪽을 조회·병합해 커서 페이지 처리 |
| 친구 코드 입장 | 종료되지 않은 대국의 `code`에 부분 UNIQUE 인덱스. 종료 대국의 코드 재사용 허용 |
| 대국 수순 | `game_moves(game_id, ply)` PK로 순서 조회 |
| 점수 그래프 | `rating_events(player_id, at, id)` |
| 최근 반복 대진 | 참가자 ID를 정렬한 `pair_low`, `pair_high`, `finished_at` 복합 인덱스. 같은 두 사람의 색·시간 모드를 합쳐 검사 |
| 시간 초과 대상 | 진행 중 대국의 `deadline_at` 인덱스. 수가 저장될 때 마감 시각 갱신 |
| 순위표 | `player_ratings(rating DESC, player_id)`를 기본으로 현재 순위 자격을 필터한 뒤 50명 제한 |

순위 자격의 유효 RD는 `rating_at` 이후 경과 시간에 의존한다. 저장된 RD만 비교하거나 먼저 상위 50명을 자른 뒤 필터하지 않는다. 현재 함수를 적용해 자격을 판정하고 부족하면 추가 후보를 읽거나, 검증된 동등 SQL로 필터한 뒤 LIMIT를 적용한다. 조회는 점수 원본과 `rating_at`을 바꾸지 않는다.

반복 대진 제한은 현재 정책(24시간, 사람 간 제한 없이 평가하는 두 판, 6수 미만 기권·시간패 제외)을 그대로 유지한다. 마이그레이션을 계기로 점수·순위 정책을 바꾸지 않는다.

`EXPLAIN QUERY PLAN`과 대표 데이터로 실제 인덱스 사용을 확인한다. 참가자 조회·기보 조회·반복 대진 검사가 전체 대국을 메모리로 불러오지 않도록 한다.

## 4. 저장의 원자성과 동시성

기존 `store.data`를 직접 바꾼 다음 `save()`를 호출하는 구조를 제거한다. DB 저장이 성공한 결과를 권위 있는 상태로 삼는다.

### 한 수 처리

1. DB worker의 짧은 쓰기 트랜잭션에서 대국·수순을 읽는다.
2. 참가자, 진행 상태, 예상 `revision`과 `ply`, 차례, 남은 시간, 합법 수를 확인한다.
3. 수와 필요한 강제 패스를 순서대로 삽입한다.
4. 시계, 마감 시각, `ply_count`, `revision`, 갱신 시각을 함께 갱신한다.
5. 종국이면 아래 종료 처리까지 같은 트랜잭션에서 수행한다.
6. COMMIT 성공 후 메모리 캐시와 WebSocket을 갱신한다.

실패하면 전체 변경을 롤백하며 성공 메시지를 보내지 않는다. ACK 이후 프로세스가 종료되어도 재접속 시 저장된 상태를 제공한다. COMMIT 이후 통신만 실패한 경우 재요청은 과거 ply/revision으로 거부하고 최신 상태를 돌려준다.

### 대국 종료 처리

종료 상태·양측 레이팅·승패·평가 횟수·최고/최저·이력·점수 제한 사유를 하나의 트랜잭션으로 기록한다. 기권, 시간 초과, 봇 응수의 동시 도착도 같은 경로를 사용한다.

- 이미 종료/정산된 대국은 다시 반영하지 않는다. 조건부 상태 갱신과 `rating_applied_at`, 대국별 이력 고유키를 함께 사용한다.
- 제한된 승리의 점수 증가 금지, 제한된 패배의 점수 감소, AI 점수 고정 등 현재 정책을 보존한다.
- 이력이 남지 않는 경우까지 포함해 대국 전체 정산은 정확히 한 번 실행한다. 고유키만으로 전체 정산의 중복을 막았다고 판단하지 않는다.
- 기존 종료 대국은 이전 과정에서 정산 완료로 표시하며 다시 계산하지 않는다.
- AI 추론·네트워크·장시간 통계를 트랜잭션 안에서 기다리지 않는다. AI 결과도 예상 revision을 검사한 후 적용한다.

Repository의 주요 명령은 `authenticate`, `createPlayer`, `createGame`, `joinGame`, `applyMove`, `finishGame`, `listPlayerGames`, `getLeaderboard`, `getRatingHistory`, `getDueGames`로 구성한다. 여러 쿼리를 호출자가 임의로 조합해 정산하지 않도록 업무 단위 명령을 제공한다.

## 5. 인증과 클라이언트 호환

기존 토큰의 난수 값을 SHA-256으로 해시해 저장하고 로그인 요청의 해시를 비교한다. 현재 토큰은 고엔트로피 난수이므로 비밀번호 저장과 별개의 정책이다. 토큰 원문·해시는 운영 로그에 남기지 않는다.

기존 클라이언트는 `welcome.token`을 다시 저장하므로, 해시만 저장한 서버가 기존 토큰을 DB에서 복원해 전송하려 해서는 안 된다. 인증 성공 시 클라이언트가 제출한 유효 원문을 그 연결의 응답에 사용한다. 신규 계정은 생성 시 한 번 얻은 원문을 응답한다. 기존 서버 URL과 토큰을 유지하면 DB 전환 자체로 재가입하지 않는다.

서버 주소 변경 시 localStorage 토큰 키가 바뀌는 문제는 DB 전환과 별개다. 1차 전환은 접속 URL과 WebSocket 메시지 형식을 유지한다. 인증 복구·이메일 로그인은 후속 제품 기능으로 분리한다.

설정·퍼즐·로컬 AI 기보는 현재 저장소를 유지한다. 후속 동기화가 필요하면 `player_settings`, `puzzle_attempts`, `puzzle_progress`를 별도로 설계한다. 점수에 영향을 주는 퍼즐 결과는 클라이언트 점수를 그대로 신뢰하지 않고 서버 검증·중복 방지·오프라인 충돌 정책부터 정한다. 분석 캐시는 재생성 가능하므로 1차 서버 DB에 넣지 않는다.

## 6. JSON 이전·검증·전환

### 도구

- `db:migrate`: 새 빈 DB 생성과 버전별 SQL 적용. 적용 이력 체크섬이 달라지면 실패.
- `db:import-json`: 원본 파일 SHA-256과 이전 식별자를 기록하고 새 staging DB에만 가져오기. 기존 운영 DB에 덮어쓰기 금지.
- `db:verify`: 구조·건수·필드·기보·레이팅 보존 보고서. 토큰은 해시 일치 여부만 보고.
- `db:backup` / `db:restore-check`: 일관된 백업과 격리 복원 검사.

위 명령은 구현할 인터페이스이며 현재 존재하는 명령이 아니다.

### 사전 검증

1. 원본 사본으로 먼저 실행한다. ID·참가 관계·코드 중복·토큰 중복·수순·숫자·시각을 검사한다.
2. 기존 누락 필드는 현재 `initializeRatingRecord`의 의미와 동일하게 보정하며 보정 내역을 보고한다.
3. 모든 플레이어·대국·수순과 저장된 전적·점수를 보존한다. 15개 로컬 대국으로 전체 전적을 재계산하지 않는다. 파일에 없는 대국과 과거 AI 보정 자료가 있을 수 있다.
4. 과거 `historyComplete=false`를 유지한다. 삭제된 이력·대국별 과거 RD·원래 없던 시각은 추측해 복원하지 않는다.
5. `integrity_check`, `foreign_key_check`, 원본 필드 비교, 기존 토큰 로그인, 전체 기보 재생과 결과 일치를 확인한다. 불일치는 숨기지 말고 보고하고 해결 전 전환하지 않는다.
6. 동일 입력의 반복 실행이 운영 중 중복 계정·이력·대국을 만들지 않는지 검사한다. 실패한 staging DB는 운영 경로로 승격하지 않는다.

### 실제 전환

1. 대국이 없는 시간을 우선 선택하고 새 방·매칭 생성을 중지한다. 빠른 시계 대국은 종료 후 전환한다.
2. 서버를 정상 종료하여 JSON을 최종 flush하고 원본·체크섬·이전 코드·환경 설정을 보존한다.
3. 실제 운영 원본으로 staging DB를 만들고 검증한다. 중단 시간에도 시계가 흐르는 현재 정책을 유지하므로, 남아 있는 daily 대국의 마감과 재시작 시 시간 초과 처리를 확인한다.
4. 설정을 `STORAGE=sqlite`, `DB_PATH=...`로 변경하고 검증한 DB로 시작한다. 기존 환경변수 `DATA`와의 전환 규칙을 명시한다.
5. 기존 토큰 재접속, 최근 기보, 레이팅·순위, 친구 대전, 봇 응수, 서버 재시작을 확인한다. 테스트 전적을 실제 사용자 데이터에 섞지 않도록 스모크 검사는 격리 DB에서 우선 실행한다.
6. DB가 준비되고 쓰기가 검증된 뒤 매칭을 재개한다. DB 준비 실패 시 새 빈 저장소로 자동 기동하지 않는다.

### 되돌리기

전환 후 쓰기를 재개하기 전에는 이전 코드·원본 JSON으로 복귀할 수 있다. 쓰기를 재개한 뒤 예전 JSON으로 돌아가면 신규 수·전적·계정이 유실된다. 따라서 운영 개방 이후의 기본 복구는 SQLite 백업과 호환 코드로 수행한다. JSON으로의 완전한 역변환은 토큰 원문이 해시에서 복구되지 않는 이유까지 포함해 별도 설계·검증 없이는 지원하지 않는다.

## 7. 배포와 운영

시작 설정은 WAL, `synchronous=FULL`, 연결별 `foreign_keys=ON`으로 한다. 쓰기 연결은 하나로 유지하고 충돌 재시도는 제한된 시간 안에서 수행한다. 설정 적용 후 실제 값을 읽어 검증한다. FULL은 전원 장애 시 커밋 내구성을 우선한 선택이며 실제 저장장치가 동기화 요청을 지키는지도 중요하다. [WAL 내구성](https://www.sqlite.org/wal.html), [PRAGMA](https://www.sqlite.org/pragma.html), [외래키 설정](https://www.sqlite.org/foreignkeys.html)

- 파일·디렉터리는 기존 서비스 계정 전용으로 유지한다. systemd `ReadWritePaths`에는 DB와 WAL/SHM 생성에 필요한 디렉터리 쓰기 권한을 부여한다.
- DB는 로컬 저장장치에 둔다. 네트워크 공유 폴더에서 WAL DB를 직접 운영하지 않는다.
- 기존 `server.mjs` 단일 번들만 배포하는 방식에 DB worker 산출물, SQL 마이그레이션, Linux ARM64 네이티브 드라이버를 포함한다. Windows용 네이티브 모듈을 복사하지 않는다.
- `better-sqlite3` 버전·Node 런타임·내장 SQLite 버전을 잠그고 실제 ARM64 배포 패키지로 실행·백업·복원까지 검증한다. 네이티브 모듈을 external로 둘지 정하고 로더 경로를 테스트한다. [드라이버 문서](https://github.com/WiseLibs/better-sqlite3), [API 문서](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)
- 실행 중 DB 파일 하나를 gzip 하는 기존 JSON 백업 스크립트를 교체한다. Online Backup API로 독립 스냅샷을 완성한 후 검사·압축·파일명 확정 순으로 처리한다. [공식 백업 방법](https://www.sqlite.org/backup.html)
- 초기 백업 제안은 매시간 48개, 일별 14개, 배포 직전 별도 1개이다. 별도 장치로 일 1회 복사하는 작업을 구성한다. 같은 SD카드 안의 백업은 장치 고장 복구 수단이 아니다.
- 제안 복구 목표는 로컬 장애 RPO 1시간, 별도 장치 백업 기준 장치 장애 RPO 24시간, RTO 30분 이내다. 실제 복원 연습으로 검증한 뒤 운영 목표로 확정한다.
- 매월 격리 경로에 백업을 복원해 무결성·기보 조회를 검증한다. 백업 실패·최근 성공 시각·디스크 여유·DB/WAL 크기·쓰기 지연·BUSY 오류·worker 실패를 기록한다.
- `/health`는 DB 읽기 및 worker 준비 상태를 포함하되 내부 경로·계정·토큰을 노출하지 않는다. 쓰기 실패는 별도 오류 지표와 처리로 감지한다.
- 관리 도구는 일관된 백업 사본을 읽기 전용으로 열도록 한다. 운영 중 결과·전적을 GUI에서 직접 수정하지 않는다. 정정은 근거와 변경 전후를 남기는 별도 명령으로 처리한다.
- 대국·수순·레이팅 이력은 1차에 자동 삭제하지 않는다. 보관 기간과 요약·압축은 실제 성장량을 측정한 후 결정한다.

## 8. 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 드라이버·DB worker·ARM64 패키징 검증 | 실제 배포 형태에서 DB 생성·커밋·재기동·백업 성공 |
| 2 | 마이그레이션·제약·Repository·JSON importer | 사본의 ID·토큰 인증·점수·전적·기보·불완전 이력 보존 검증 |
| 3 | 온라인 생성·입장·수·종료·랭킹·이력의 DB 경로 전환 | 직접 `store.data` 변경 제거, 기존 프로토콜과 레이팅 정책 유지 |
| 4 | 실패·경쟁·복구·부하·배포 검사 | 중복 정산 0, 반쪽 저장 0, ACK된 수의 강제 재시작 복구, 복원 성공 |
| 5 | 운영 이전 리허설 후 전환 | 운영 스냅샷 검증, 개방 전 복귀 리허설, 백업 타이머 정상 |
| 후속 | 계정 복구·기기 간 동기화·운영 화면 | 서버 DB 전환과 분리해 제품 요구사항 확정 후 수행 |

필수 검증 시나리오는 같은 수 재전송, 오래된 revision, 시간패와 착수 경쟁, 종료 중복 실행, 서로 다른 대국의 같은 플레이어 점수 갱신, 제한된 패배와 봇 점수 고정, DB 오류·디스크 부족, 강제 종료 후 재기동, 레거시 이력 보존, 운영 백업 복원이다. 기존 규칙·서버·레이팅 테스트와 typecheck/build 및 실제 배포 패키지 검사도 통과해야 한다.

부하는 실제 파이에서 10개·50개·100개 동시 대국을 순서대로 측정하고 사람 간 대국과 AI 추론 포함 부하를 분리한다. 초기 목표는 DB 쓰기 명령 왕복 p95 50ms 이하, 요청 기인 이벤트 루프 지연 p95 20ms 이하, 정상 부하에서 BUSY 실패 0이다. 목표치는 보장값이 아니며 저장장치·추론 부하 측정에 따라 조정한다.

애플리케이션 서버 다중화, 고가용성 요구, 반복되는 쓰기 대기, 운영 목표를 넘는 조회·쓰기 지연이 발생하면 PostgreSQL 전환을 재검토한다. 이때 SQL 저장 계층뿐 아니라 매칭 대기열·접속 상태·봇 작업의 소유권과 서버 간 전달도 함께 설계한다. 인원수 하나로 전환 시점을 결정하지 않는다.
