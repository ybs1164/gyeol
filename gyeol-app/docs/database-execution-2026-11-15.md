# SQLite 전환 구현 및 검증 결과

2026-11-15, Windows x64 / Node v22.14.0. 드라이버 `better-sqlite3` 13.2.0, 내장 SQLite 3.54.1.

## 완료한 변경

SQLite/WAL 저장소, 전용 DB worker와 비동기 Repository를 구현했다. 착수 검증·수순·시계 및 대국 종료·양측 점수·전적·이력은 각각 한 트랜잭션에서 커밋하고 나서 클라이언트에 알린다. 사람·AI 정책과 기존 API를 유지한다. 서버의 직접 `store.data` 변경은 제거했다.

토큰 원문은 새 DB에 저장하지 않는다. 해시 조회와 요청 토큰 반환으로 기존 재접속을 유지한다. 외래키·고유키·CHECK·인덱스, 규칙/초기 배치, 스키마 체크섬과 이전 실행 이력을 추가했다. 기존 JSON Store는 과거 보정 회귀 테스트에만 남겼다.

`db:migrate`, `db:import-json`, `db:verify`, `db:backup`, `db:restore-check`를 추가했다. 이전은 staging DB의 원본 비교 검증 후 승격하며 기존 DB를 덮어쓰지 않는다. 빈 DB 자동 기동과 알 수 없는 스키마 기동을 차단했다.

파이 패키지에 DB worker·SQL·CLI·Linux ARM64 네이티브 드라이버·운영 안내를 넣었다. 설치 시 격리 DB의 실제 AI/대국/백업/복원을 먼저 검사하고 유지보수 게이트로 클라이언트 쓰기를 막은 상태에서 이전한다. 개방 전 실패한 첫 이전 DB는 별도 보존하므로, 구 JSON 서버가 다시 시작된 뒤 재시도할 때 낡은 SQLite를 재사용하지 않는다.

시간별 Online Backup API 백업과 격리 복원 검사를 설정했다. 시간별 48시간·일별 14일 보관이며 JSON 원본·배포 직전 백업은 보존한다. 실제 운영 설정 방법은 [운영 안내](database-operations.md)에 있다.

| 검사 | 결과 |

| 전체 테스트 | 25개 파일, 141개 통과 |
| 유지보수 게이트 추가 후 DB 회귀 검사 | 10개 통과. 앞선 전체 실행의 DB 9개를 포함해 고유 테스트 총 142개 검증 |
| 최종 typecheck | 통과 |
| 웹·서버 빌드 | 통과 |
| 모바일 레이팅 UI | 390×844, 한국어·영어, 기존 이력·제한 사유·레이아웃 검사 통과 |
| 빌드된 서버 패키지 실행 | HTTP 자산, 친구 대전 완주, 토큰 재접속, 저장 기보 조회 통과 |
| 실제 AI | 격리 DB에서 매칭·합법 응수·기권 처리 통과 |
| 백업·복원 | Online Backup API 및 격리 복원 무결성·기보 검사 통과 |
| 배포 스크립트 | Bash 문법 검사 통과 |
| ARM64 패키지 | 필요한 파일, ELF AArch64 바이너리, 파일별 SHA-256, 사용자 DB·서명 키 제외 확인 |

DB 회귀 검사는 원본 보존과 잘린 이력, 토큰 원문 미저장, 실패 이전, 중복 수, 두 DB 연결의 종료 경쟁, 정산 중 강제 SQL 실패의 전체 롤백, 시간패와 늦은 수 경쟁, 유지보수 중 계정 생성 차단, 백업 덮어쓰기 거부, 누락 DB·변경된 스키마 거부, 응답 받은 수의 프로세스 강제 종료 후 복구를 포함한다. 쓰기 실패 시 health 불량과 성공 후 복구도 확인했다.

패키지 검사에서 기존 스모크 도구의 `수순 = 이전 + 1` 조건이 자동 패스의 두 수 증가를 놓치는 문제를 수정했다. 현재는 수순 증가를 기다리며 대전을 정상 완료한다.

## 로컬 부하 기준값

`npx tsx tools/bench_database.ts --output packages/server/data/sqlite-benchmark.json`으로 임시 DB에 각 3회씩 동시 착수 요청을 보냈다. AI 추론·WebSocket·실제 파이는 포함하지 않는다.

| 동시 대국/한 번에 보낸 쓰기 | 쓰기 요청 수 | 오류 | 대기 포함 왕복 p95 | 이벤트 루프 지연 p95 |
|---|---:|---:|---:|---:|
| 10 | 30 | 0 | 40.4ms | 5.4ms |
| 50 | 150 | 0 | 167.2ms | 4.4ms |
| 100 | 300 | 0 | 329.9ms | 4.3ms |

한꺼번에 몰리는 50·100건 쓰기는 최초 제안의 50ms 목표를 넘었다. 개별 명령의 실행보다 직렬 커밋을 기다리는 시간이 늘어난다. 내구성 우선의 FULL 설정은 유지하며, 현재 소수 이용자용 배포와 큰 동시 쓰기 부하를 구분한다. 이 결과를 파이 동시 접속 수나 운영 처리량으로 환산하지 않는다.

## 남은 운영 작업

- 실제 파이의 SSH 접속 대상이 제공되지 않아 원격 배포·운영 DB 전환은 수행하지 않았다.
- Linux ARM64 바이너리는 패키지에 포함하고 형식을 확인했지만 실제 ARM64 실행은 해당 장치의 설치 전 검사에서 확인해야 한다.
- 파이에서 AI 포함 10/50/100 동시 대국과 저장장치 지연을 측정한 뒤 운영 한도를 확정한다.
- 외부 백업 장치의 경로·접속 정보가 없어 외부 복사와 장치 장애 복구 목표는 아직 검증하지 않았다.
